## Request

1. A released requirement can be iterated any number of times. The owner changes the SAME requirement (corrections: "what you built is fine, but change these things"), presses Update/Validate, the validating agent asks specific questions, the owner answers, and Start run becomes available again. Verified by a backend test: released requirement, edit, validate, answer every point, GET the item: Start allowed (200, not 409); repeated three times in a row.
2. Unlock rule: Start run is enabled when EITHER the text was approved, OR the owner has resolved EVERY point of the latest validation round (each point applied, declined, or answered). An unresolved point keeps Start disabled and the banner says how many are left ("2 of 5 points resolved"). Saved text that differs slightly from the proposal (owner removed a pasted paragraph, reworded) does not break the unlock: what counts is that the points were resolved. Verified by a test with a saved text different from the proposal.
3. The round counter works: it increases at every validation, also after the owner applies or edits (today requirement #169 shows five rounds all logged as "round 1" and validation_rounds = 1, so "Accept as is" never appears). It resets only when the owner starts a new iteration after a release. From round 3 "Accept as is, start anyway" is always offered. Verified by a test of three rounds with edits in between. First find and write the cause in the task comment (see backlog/routes.ts around lines 575-580 and backlog/backlogStore.ts setValidation/resetValidationRounds).
4. The validating agent classifies the change as ITERATION (same requirement: corrections, things the owner does not like) or EXTENSION (new functionality added). For an ITERATION it asks only the specific questions needed and the owner can go on. For an EXTENSION the banner says so and offers a "Create linked requirement" button that creates a new requirement depending on this one (depends_on = this requirement) with the new text; the owner may still choose "Treat as iteration". Verified by prompt and parser tests and by a screenshot.
5. Under the validating agent's answer every point has its own buttons: Apply (puts the proposed wording in the text), Decline (with an optional short note), Answer (a field for questions). A footer shows "N of M points resolved" and the buttons "Update requirement" and "Accept as is, start anyway". Points the agent marks BLOCKING but that cannot be done (for example a technical impossibility already known from the build) are not BLOCKING: it checks the build/install history first. Verified by a frontend test and screenshots, dark and light.
6. The run of an iteration reuses the requirement's worktree and branch, builds again, ends at "Ready to release", and the owner presses Release again. No new requirement is created for an iteration. Verified by a runner test and by the PBI change log entry.
7. The banner always says in one English line what the owner has to do next, and the page updates live without a reload (as MIC-438). Verified by a frontend test.
8. Requirement #169 is the acceptance case: with the open validation, the owner answers the points and can press Start run. Do not start the run: the owner does it. Verified by the item state.
9. Tests and builds pass; English texts only; update Process.md and the validation prompt; commit, push, queued restart. The final reply says when #169 can be started.
