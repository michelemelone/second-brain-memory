## Request

ACCEPTANCE CRITERIA
1. DELETE /backlog/:id no longer rejects states other than Release (test: a PBI in Test, Backlog and Release is deleted).
2. Removal runs from the footprint of MIC-451, also when there is no deployed ref or worktree (test: footprint with keys but no ref still withdraws the records).
3. Records leave the instance through a cleanup deploy; the deploy script check that nothing else goes is kept (test).
4. Source code of the requirement is removed from the Fluent project in the same cleanup (test on fixture repo).
5. A PBI released in a first step whose second step failed has both steps removed (test).
6. If the cleanup deploy fails, the PBI and its files are left untouched and the error is returned with the reason (test).
7. Only after success: branch, worktree, refs, docs, leftovers, attachments and the PBI are removed (test).
8. Records only modified by the requirement are never deleted (test).
9. An active run still needs stopRun=true, as today (test).

Context: today DELETE /backlog/:id (backend/src/backlog/routes.ts) and the trash button (frontend PbiTab.tsx, canDeletePbi) allow only state Release (introduced by MIC-214, after MIC-206). withdrawRequirement (applications/withdrawRequirement.ts) acts only when a worktree and a deployed ref exist, otherwise returns null and removes nothing. Goal: the owner can delete a PBI in ANY state and everything it left in Fluent source and on the platform is found and removed. Rule agreed with the owner: only records CREATED by the requirement are removed; records it only modified are listed as 'not touched'. Never force or guess: if something cannot be located, say so. Depends on MIC-451 (footprint scan).

**What I chose:**
- **Refusal on unreadable data:** the delete is refused, with nothing removed, if the scan could not read the git source, `state.json`, a deployed ref or the branch. This follows "never guess".
- **Failed source revert:** if the records are off the instance but the source revert on `main` fails, the PBI is kept and the error says so. Deleting again after fixing `main` finishes the job.
- **Revert conflicts:** a conflict in the generated `keys.ts`, or in the requirement's own docs folder, is resolved automatically. Any other conflict stops the revert and leaves `main` as it was.
- **Push:** the revert commit on `main` is pushed, like a release.

**Not done:**
- The trash button in the frontend still shows only for state Release. That is MIC-453.
- Modified-only records are never deleted, but the cleanup deploy installs the source as it stands in `main`. Any change the requirement made to a shared record is not undone.
