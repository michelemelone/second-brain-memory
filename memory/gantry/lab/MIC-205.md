**Finding A, retry storm (the biggest waste).**
- On 2026-10-13, between 19:00 and 20:42, the requirement `meeting-room-av-equipment-request` started a new run about every 4 seconds (median gap 3.95 s). Each run died immediately on the session limit ("resets 10:40pm Europe/Zurich").
- That is 1,048 failed runs, costing about $4.2 and 1 h of recorded run time. Each one also loads the full startup context.
- 942 of the log files are an identical 22,264 bytes, which shows the same failure repeating.
- The guard exists now. `runner/runTrigger.ts` has `MAX_LIMIT_STREAK = 3`, a retry time parsed from "resets …" (`classifyFailure.ts`), and `RETRY_SOON_MS = 5 s`. It arrived with commit `0b18e4a` on 2026-10-26, after the storm.
- Weak spot: the streak counter (`limitStreak`) is an in-memory `Map`. A restart resets it. If no reset time can be parsed, the retry falls back to 5 s. I read the code but did not reproduce either case.

**Finding B, session-limit stops are common even outside the storm.**
- Every non-storm failure I found was the same session limit (9 more runs, resets at 6:30pm, 9:40pm, 11:50pm, 1:30am, 12:30am, 9am).
- A requirement dies mid-pipeline and waits for a human or for the timer.
