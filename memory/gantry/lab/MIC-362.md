## Request

1. The requirement chat offers exactly two actions for a change: "Update this PBI" (in place, written to the Change log) and "Add sub-task (1 level)"; there is no third path that creates a new PBI from that chat. Verified: read the chat, press every proposed action, and attach screenshots of both cards.
2. On a level-2 item the chat offers only "Update this PBI": no "Add sub-task" and no way to create a grandchild, and the server refuses it if requested directly. Verified: open the chat on a child, screenshot, and curl that attempts the creation returning 4xx.
3. "Add sub-task (1 level)" creates a child with related_to set to the current PBI, the same Application, Feature and tags, and Description and Acceptance criteria filled from what was agreed in the conversation, never empty. Verified: create one from the chat and paste the resulting fields.
4. The child starts by itself when the parent is released, as a Lab task with a blocker does, and while the parent is not released it stays waiting with a visible "waiting for the parent" state. Verified: create a child on a released parent and see it start with no click; create one on a non-released parent and see it wait, then release the parent and see it start; screenshots of both states.
5. "Update this PBI" never starts a run by itself: it writes the Change log and leaves a pending run that starts only when the owner presses "Start run". Verified: ask for a change on a released PBI, confirm no run starts, then press Start run and see run 2 start; screenshots.
6. The old entry points are gone or redirected: the "Add change" and "Add bug" buttons on the PBI header no longer create an empty child, and no flow in the app can end in "409 Delivery already started". Verified: search the web code for the old endpoints and buttons, and walk the flows; grep output and screenshots.
7. A full end-to-end demo on a disposable requirement, with evidence attached: create it, deliver it once (run 1), ask a change in the chat (Change log + Start run + run 2), create a sub-task from the chat and see it start when the parent is released. Verified: screenshots plus excerpts of state.json and PBI.md for every step.
8. Automated tests cover the chat action routing (update vs add sub-task), the filled fields of a new child, the no-run-on-update rule and the no-grandchild rule. Verified: test run output, all green.
9. `npm run build` passes in programs/server and programs/web, the app is restarted through the project restart queue and the requirement screen and its chat load without console errors. Verified: build output and pages in the embedded browser.

CONTEXT
Confirmed by the owner: the requirement chat becomes the single entry point, like the bigMike Lab where writing in chat updates the same task and can create one level of sub-task. Today the chat on a requirement proposes an in-place rewrite with no history, "Add change" creates an empty child that does not start, and a chat that cites "#129" creates another child; nothing starts automatically. This task depends on the other three: hierarchy limit, PBI.md Change log and numbered runs. UI work must keep MIC-286 (Lab-like layout) intact. Related: MIC-286, MIC-290, MIC-310.
