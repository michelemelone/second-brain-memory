## Request

1. A change request written in a requirement's chat updates the same item (description and/or acceptance criteria) and appends a dated entry to the Change log section of its PBI.md; it does not create a new backlog item. Verified by making a change in the chat and diffing the item and PBI.md.
2. The Change log keeps every earlier entry: a second change appends a new dated bullet and nothing is overwritten. Verified with two successive changes and the resulting PBI.md.
3. "Add change" creates at most a level-2 sub-task linked to the parent; a sub-task never shows "Add change" or "Add bug". Verified on screen and with an API call that attempts a third level and gets HTTP 400.
4. The parent requirement screen lists its sub-tasks with their state and opens them; the sub-task screen shows which parent it belongs to. Verified with screenshots of both screens.
5. The PBI.md is the memory used by the feature knowledge base and the retrospective: a change written in the Change log appears in the regenerated knowledge base or retrospective evidence. Verified by regenerating one feature's knowledge base and reading the output.
6. Backend tests, frontend tests and both builds pass. Verified by the commands' output.

Context and analysis
Michele wants Gantry to behave like the bigMike Lab: you write a change in chat, the same task is updated and a dated Change log entry is appended under the requirement — you do not open a new task. In Gantry today "Add change" creates a new item through related_to, with no depth limit, and the change is a new document set.

This task depends on the single PBI.md (the Change log section lives there) and on the two-level cap (a change is either an update of the same item or a one-level sub-task).

Related tasks: MIC-205 (analysis), MIC-222 (what a PBI chat can reach), MIC-290 (Describe panel / chat).
