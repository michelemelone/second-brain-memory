# MIC-438: Gantry: the requirement page updates live when a run starts, progresses and ends (no manual refresh)

- Project: Gantry
- Status: done
- Priority: high
- Agent: Pegasus

- Updated: 2026-11-23

## Request

ACCEPTANCE CRITERIA
1. After the owner presses Start delivery / Start run on the requirement page, the page updates by itself with no manual refresh: within 2 seconds the strip shows "Run N in progress - the requirement is read only until it finishes", the Start button is disabled, the fields become read only, the state changes (New to Documentation) and the Live tab starts showing the run. Verified by a frontend test (mocked start call then item state) and a screenshot taken without reloading.
2. While a run is going the page keeps itself live: the state, the stage dot, the Live tab and the run strip follow the server (live push or a light poll of the item, 2-3 seconds, stopped when the page is closed or hidden). Verified by a frontend test with fake timers and by watching a real run.
3. When the run finishes (Ready to release, failed or stopped) the page unlocks by itself: read-only is lifted, the strip and button show the new state, and the run result appears, with no refresh. Verified by a frontend test and by watching a run end.
4. The same live behaviour applies to the Sprint / Backlog table row and to the previous/next navigation of the page (the row shows the live dot and the new state without a reload). Verified by a test and a screenshot of the table during a run.
5. No flicker and no loss of what the owner is typing: a live refresh never overwrites unsaved edits in the form (only the run/state fields are updated). Verified by a test that types while a refresh arrives.
6. Every user-facing string is in English; frontend tests and build pass; committed, pushed, restart queued.

ANALYSIS (MIC-363, MIC-377, MIC-437)
Owner report on requirement #169: after pressing Start delivery he had to refresh the browser page to see "Run 2 in progress - the requirement is read only until it finishes" (screenshot). The page keeps the item it loaded in RequirementFormModal.tsx (current/setCurrent, delivering = current.delivering) and only refetches after save, validation (refreshValidationState) and a few actions, so the state set by the server when the run starts never reaches the open page. Fix like a live view (the jQuery-style behaviour asked by the owner): refetch the item right after the start call returns, then keep it in sync with a light poll or a server push while delivering, and once more when the run ends. Files: gantry/frontend/src/components/backlog/RequirementFormModal.tsx, the page that passes onStartDelivery, api/backlog.ts, the backlog table.

## Last report of the agent

**What changed (frontend only)**
- **Poll hook:** a new `useLivePoll` hook polls every 2.5 s and skips ticks while the page is hidden. It stops when the page closes or the poll is switched off.
- **Requirement page:** `RequirementDetailPage.tsx` re-reads the item and the Backlog list while a run is going. It also does this for 10 s after a start or a save, until the server marks the run.
- **Start button:** `PbiTab.tsx` re-reads the item right after the start call returns, so the strip, the state change and the lock appear at once.
- **Form:** `RequirementFormModal.tsx` takes the run and state fields from the refreshed item. The state field moves only if the owner has not edited it. Typed fields are never overwritten.
- **Backlog table:** `BacklogPage.tsx` now polls every 2.5 s while any row is running, instead of every 10 s. The previous/next navigation reads the same refreshed list.
