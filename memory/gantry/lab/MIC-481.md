## Request

1. In the Sprint Backlog table, a row whose item has `delivering = true` shows in the State column a chip reading "In progress" instead of the stored stage, with a small dot inside the chip that pulses (`animate-pulse`, `motion-reduce:animate-none`) in a colour of its own — the same blue family as the Lab's "In progress" badge, different from all six stage chips. Verified by a vitest case in `tests/StateBadge.test.tsx` that renders the chip with `delivering` and asserts the text "In progress", the pulse class and the reduced-motion class, and that the six stage chips keep their own texts; plus a screenshot of the live Sprint Backlog while a delivery runs.
2. In that state the chip carries an `aria-label` and a `title` naming the work: who runs it, the engine and the model, the requirement and since when, in the form `<Agent title> · <Engine> · <model> · since HH:MM — #<id> <title>`, built from the Board data the seats banner already reads (`fetchBoard`: `card.run.agents[0]`, `engine`, `model`, `since`, `card.backlog.id`) joined to rows by backlog id. When the Board has no card for that requirement the text is `Delivery running since HH:MM` from the row's `delivery_started_at`, and `Delivery running` when that is null: no agent, engine or model is ever invented (the same rule the seats banner already follows with "not recorded"). Verified by a `BacklogTable` test with a delivering row and a matching board card asserting the exact tooltip, and one with no card asserting the fallback.
3. Exactly one Board poller feeds both the seats banner and the chip: `BacklogPage` reads the Board every 5 s through `useSeatBoard` and passes it down (`SeatsBanner` accepts the board it is given and keeps reading by itself only when it is not), so the page makes one Board request per interval, not two. Verified by a test that counts `fetchBoard` calls over one interval, and by the network panel of the live page.
4. The stored state never changes: the requirement keeps its saved stage (for example Release) in the data, in the API and next to the title, and grouping, sorting and the State column filter keep reading the stored stage, so a requirement delivering while in Release is still found by filtering Release and still sits in its Board column. Verified by unit tests on the group/sort/filter functions with a delivering row and by checking #176 on the live page during a run.
5. When the delivery ends the chip returns to the stored stage at the next Board poll, with no reload, and the dot before the title stops as it does today. Verified by a `BacklogTable` rerender test going from `delivering = true` to `false`, and on the live page after #176's run finishes.
6. The dot before the title (`StateDot`) and its behaviour stay as they are: this change only adds the live reading inside the State chip. Verified by the existing `StateDot` / `BacklogPage` tests passing unchanged.
7. The State cell stays read-only while delivering (no state change from the table mid-run) and keeps its click-to-change menu on every other row. Verified by the existing `BacklogRowActions` tests plus one asserting the cell is disabled while delivering.
8. The chip keeps `data-state` = the stored stage and adds `data-live="true"` only while delivering, so nothing that reads `data-state` breaks. Verified by the `StateBadge` tests.
9. `npm test` in `frontend` is all green and `npm run build` succeeds. Verified by the command output pasted in the report.
10. Shipped live: the frontend built and served by the running app, with a screenshot of the Sprint Backlog showing #176 as "In progress" while its delivery runs and back to Release afterwards. The backend is touched only if the Board data does not already carry what point 2 needs; in that case the backend is built and `bigmike-restart Gantry` is queued, never a restart run directly. Verified by the commit hash, the screenshot path and, when relevant, the queued restart.
