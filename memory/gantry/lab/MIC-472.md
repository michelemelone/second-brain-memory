**Left on the instance by design, for the owner to remove by hand**
- Table `u_zz_mic472_proof` (`sys_db_object bf9a3d9dc3b09710147bd71d05013134`, label "ZZ MIC-472 Proof") with its 10 `sys_dictionary` rows (incl. `u_name`, `u_state`, `u_detail`), 10 `sys_documentation` rows and 4 `sys_choice` rows (two of them the orphans of D2, element `state`). The delete keeps a table on purpose; `Artifacts → Deleted requirements` shows it and Check on instance answers `exists`.
- Local Update Set `Gantry #204 zz-mic472-global-proof` (`7a9ab99dc3b09710147bd71d050131d9`, state `complete`): update sets are protected by design (MIC-471, criterion 3), and the delete result does not name it (D5).

**Defects found (cause, not hidden)**
- **D1 — Check on instance and the footprint read 3 of the 11 records.** `extractAllRecordRefs` / `extractRecordRef` (`backend/src/artifacts/extractRecordRef.ts`) takes the table and sys_id from the entry name `<table>_<32 hex>`, else from `<payload><![CDATA[…]]>`. In this delivery most payloads are **XML-escaped** (`<payload>&lt;?xml …&lt;record_update …`) and the dictionary, label and choice entries are named `<table>_<table>_<element>`, so 8 of 11 are dropped: the check says "All 3 records … are on the instance" and the footprint lists 22 `unknown` entries ("the record it changes (its table and sys_id) is not in the export"). Same function as MIC-475 (open), different case; not fixed here to keep this task a proof and not collide with MIC-475. Live on #204: 11 entries, 3 read.
- **D2 — two created records neither carried nor listed.** The run first made a `state` column with two choices, then removed the column; the platform exported a `DELETE` of the choice set instead of the two records, so `sys_choice 49aa7d9d…`/`2daa7d9d…` stay on the instance. `finish`'s `NOT CAPTURED` compares **update-entry names**, and the `DELETE` entry carries that name, so nothing was reported on the second pass, and the `Check by hand` list of §6 does not mention them. Live: both sys_ids absent from the file, present on the instance.
- **D3 — the run-2 "Released" block is written twice in PBI.md §6.** `markGlobalReleased` appends a `### Released — <date> (run N)` block and never checks for an existing one. Two identical blocks for run 2 were in §6 before the delete; the ledger holds one run 2. The runner comment about "the server's own release of verified deliveries and the runner's continuation started two releases" describes the same shape; the exact second call could not be observed because the delete removed the run log and the journal carries no release line.
- **D4 — the delete leaves `<workspace>/.gantry/global/<id>.json`.** `discardPbiFiles` removes `Global/<id>_*.xml` and `<logRoot>/<slug>` only; the delivery state `global-update-set.mjs` keeps stayed after #204 was gone (875 B, listing every record it wrote). I removed it by hand; the file is dead data for a deleted requirement.
- **D5 — the local Update Set stays on the instance and is not listed.** MIC-471 protects update sets from the cleanup, which is right, but the delete result and the leftovers list name only the table, so "check by hand" never tells the owner that `Gantry #204 …` is still under System Update Sets > Local Update Sets.
- **D6 — MIC-471's runtime script was never in the live checkout.** `programs/servicenow_ai/gantry/backend/scripts/global-cleanup.mjs` did not exist in the running tree (the tree sits on an old commit; MIC-471 shipped `dist/` only), so every boot logged `installing the workspace tools failed: ENOENT … global-cleanup.mjs`. The delete worked only because the workspace copy `servicenow_dev/scripts/global-cleanup.mjs` was already there from an earlier run; a fresh workspace would have failed a Global delete. I copied the file from `origin/main` (`aff637a`) into the live `backend/scripts/` — identical bytes, no restart needed (it is read at runtime), and the workspace tools install will refresh the copies on the next run.
