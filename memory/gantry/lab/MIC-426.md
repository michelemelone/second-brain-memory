## Request

ACCEPTANCE CRITERIA
1. A new run on a requirement goes through intake, validation, design and build of the Fluent source, runs npm run build, and then stops in a new state 'Ready to release'; it never runs npm run deploy and never touches the instance. Verified by a backend test on runTrigger asserting no deploy is started, and by state.json of a real run showing phase built done and installed not done.
2. The tester agent is reduced to a build and syntax check: it runs the build, reads the errors and fixes them in the source, then reports; it does no live verification and no instance read-back. Verified by sn-tester.md and the runner prompts, and by a test asserting the prompt carries no live-test step.
3. A short static code check runs before the build and writes one line per rule into the PBI.md Build log with pass/fail: no hard-coded sys_ids, URLs or credentials; catalog items have catalogs and categories; visibility uses User Criteria and never roles or ACLs; catalog variables are written inside CatalogItem() or VariableSet(); plus the rules in lessons.md and the best practices assigned to sn-builder. A failed rule is fixed by the builder before the run stops. Verified by a unit test per rule on a good and a bad source sample.
4. If the build fails, the agent corrects the source and rebuilds, with a cap of 3 attempts; after that the requirement shows a clear English error and stays not ready. Verified by a test with a failing build.
5. The state 'Ready to release' appears as a column/status and as a filter in the Backlog and on the requirement page, with an English tooltip saying what it means; it is decided by the server state, so a reload shows the same. Verified by screenshots of the table and the page (programs/bin/bigmike-shot gantry) in dark and light.
6. The run summary written for the owner lists, per requirement, what to check by hand on the platform after installation. Verified by reading the PBI.md of a run.
7. Existing behaviour that must stay: numbered runs on the same PBI, edit lock during a run, the Change log. Verified by the existing tests still passing.
8. Backend and frontend tests and both builds pass; committed, pushed, restart queued. Verified by the commands output and the queue entry.

CONTEXT (owner decisions, 2026-11-21). New Gantry delivery model: the owner defines and validates requirements, a run implements and compiles them, and the owner decides when to install a whole batch. Today every run does build, npm run deploy, live verification and automatic release by itself (runner/runTrigger.ts, build_agent/agents/sn-release.md, Process.md). Measured on 59 requirements: npm run build median 12 s, npm run deploy median 43 s (p90 121 s), sn-tester median 4.6 min per task. The tester becomes only a build/syntax checker that fixes build errors; the live test is done by the owner by hand on the platform after installation, so no live verification is automated. EVERY user-facing string (buttons, banners, tooltips, errors, empty states, hints) is in English only, in line with the existing Gantry rules; search the diff for Italian words. Keep the Lab-copy look (MIC-286, MIC-329): dark and light, desktop and phone. Related done tasks to respect: MIC-363 (numbered runs on the same PBI), MIC-361, MIC-362 (chat actions), MIC-415 (Action button only when there is something to release), MIC-416 (validation gate on a released requirement). Repo: gantry/programs. Memory: the Gantry brief second-brain/memory/gantry/BRIEF.md is missing; report it, do not invent it. Finish with builds, tests, commit, push and the Gantry restart queued (bigmike-restart Gantry).
