## Request

ACCEPTANCE CRITERIA
1. Applying the changes proposed by the validation counts as validated: the applied text is stored as validated_revision/validated_content, validationRequired becomes false, the banner and the "Validate with AI" button disappear and Start delivery is enabled. Verified by a backend test (propose, apply, GET the item: validationRequired=false; start returns 200, not 409) and a screenshot.
2. The owner can run as many validation rounds as he wants (2nd, 3rd, ...), each one starting from the current text, by pressing Validate again at any time, even when the requirement is already unlocked. Verified by a test with three consecutive rounds.
3. Rounds cannot go on forever. The server counts the rounds per requirement (reset when the owner edits by hand after an approval) and passes "round N" to the validating agent together with what was already proposed, applied or declined in the earlier rounds. Verified by a backend test on the prompt.
4. Blocking vs optional: the agent must label every proposal as BLOCKING (missing, contradictory or untestable point that would make the delivery wrong) or OPTIONAL (style, wording, nice to have). Only BLOCKING proposals keep the gate armed (changes_requested); a reply with only OPTIONAL proposals is recorded as approved, and the optional ones are shown as suggestions. Verified by a prompt test and a parser test.
5. From round 3 on the agent may report only BLOCKING points and must not re-propose anything the owner declined. Verified by a prompt test.
6. Escape hatch: from round 3 on the banner offers "Accept as is, start anyway" (English tooltip) that records the current text as validated with outcome "accepted by owner"; the owner is never stuck. Verified by a test and a screenshot.
7. The "validation is running" line never stays stuck after the turn ends (success, failure, reload); the banner and the "Thinking..." indicator agree. Verified by a frontend test and a reload during and after a validation.
8. Hand edits after a validation re-arm the gate as in MIC-429; the MIC-416 banner for released requirements is unchanged; every state has one English line saying what to do next; backend and frontend tests and both builds pass; committed, pushed, restart queued. Verified by the existing tests plus the new ones.

ANALYSIS (MIC-429, MIC-416)
Owner report on requirement #169: validated with AI, the agent proposed changes, the owner applied them, but the banner "This requirement is not validated yet" and the button stay and Start delivery is disabled. Cause: requirements/routes.ts records "approved" only when the validate turn returns no requirementUpdate; backlogStore.setValidation moves validated_revision only on "approved". After applying a proposal the revision differs from validated_revision, so the gate stays armed until a later turn proposes nothing, which may never happen. Owner decision (chat, 2026-11-23): several rounds are fine, but not forever; hence applying unlocks, blocking/optional split, round counter with a prompt that narrows down, and an "Accept as is" escape from round 3.
