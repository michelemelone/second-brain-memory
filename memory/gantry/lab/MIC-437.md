## Request

ACCEPTANCE CRITERIA
1. When the validating agent proposes changes and the owner applies them to the requirement (the "update" from the Conversation), the applied text counts as validated: the new revision is stored as validated_revision/validated_content, validationRequired becomes false, the banner "This requirement is not validated yet" and the "Validate with AI" button disappear, and Start delivery is enabled. Verified by a backend test (propose, apply, then GET the item: validationRequired=false; start returns 200 not 409) and a screenshot of the requirement page.
2. Only the exact text proposed by the agent is trusted: if the owner edits title, description or acceptance criteria by hand after applying (or instead of applying), the revision differs and the gate re-arms as in MIC-429. Verified by a test: apply, edit, validationRequired=true again.
3. The state "validation running" never leaves the page stuck: when the validate turn ends (success, failure or the chat is closed/reloaded) the banner leaves the "validation is running" line and shows the right next step; the "Thinking..." indicator and the banner agree. Verified by a frontend test and by reloading the page during and after a validation.
4. Every state keeps one English line saying what to do next (MIC-429 criterion 4), including the new "changes applied, validated" state. Verified by the modal tests walking the states.
5. MIC-416 banner for a released requirement and MIC-429 gate for hand edits keep working; backend and frontend tests and both builds pass; committed, pushed, restart queued.

ANALYSIS (MIC-429, MIC-416)
Owner report on requirement #169 (Maconomy engagements...): the requirement was validated with AI, the agent proposed changes, the owner applied them (the PBI was updated), but the page still shows "This requirement is not validated yet" + "Validate with AI" and Start delivery is disabled. Cause found in the code: requirements/routes.ts records a validation as approved ONLY when the validate turn returns no requirementUpdate (outcome = requirementUpdate ? "changes_requested" : "approved"); backlogStore.setValidation moves validated_revision only on "approved". So after "changes_requested" the owner applies the proposal, the revision changes, revisionOf(item) !== validated_revision, and backlog/routes.ts validationRequiredOf stays true until a second full validation turn returns zero proposals, which the agent may never do (it keeps advising). The owner's rule: after the advice, applying the update must unlock the delivery without another round. Fix: when the owner applies a proposed requirementUpdate (the apply path in the requirement chat / Conversation panel), call setValidation with outcome "approved" for the resulting content (server side, compare the applied draft with the proposal of the last turn). The screenshot also shows a validation still "running" (Thinking...) next to the banner: check that the running flag (validationRunning in RequirementFormModal.tsx) is cleared when the turn ends.
Files: gantry/backend/src/requirements/routes.ts, backlog/backlogStore.ts, backlog/routes.ts; gantry/frontend/src/components/backlog/RequirementFormModal.tsx and the Conversation panel.
