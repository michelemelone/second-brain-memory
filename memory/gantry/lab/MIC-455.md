# MIC-455: Gantry: service-account token (Bearer) for agents, admin power, hashed, revocable

- Project: Gantry
- Status: done
- Priority: high
- Agent: Pegasus

- Updated: 2026-11-25

## Request

ACCEPTANCE CRITERIA
1. The auth middleware accepts Authorization: Bearer <token> besides the session cookie; a valid token resolves to a service user with admin role and write rights, and goes through the same buildScope and policy as any admin (backend tests: admin routes, backlog routes, 401 without token, 401 with a wrong or revoked token).
2. CSRF is not required for Bearer requests, and cookie requests keep it (test).
3. The token is stored only as a hash (a salted SHA-256 or stronger); the plain value is shown once at creation (test: the stored file contains no plain token).
4. A terminal command, next to user:reset-password in auth/cli.ts, creates, rotates, revokes and lists service tokens (npm script documented; test).
5. The service user cannot log in with a password and is shown as a service account (test).
6. Requests made with the token are recorded in the history as 'bigMike (service)', distinct from people (test on one write action).
7. The token's request rate is limited like login, and a revoked token stops working at once (test).
8. No bypass or dev-login switch exists (grep of the diff).
9. The new token is created on the beedme server, saved in the server secrets file (not in the repo, not in chat) and a call to /api/backlog with it returns 200 (command output without the token value).

Context: Gantry only authenticates people (username+password, cookie gantry_session, CSRF header; backend/src/auth/*, server.ts). Lab agents and bigMike get 401 on /api/*, so they cannot verify or act on the live Gantry (see MIC-454, where Pegasus is blocked; MIC-214 and MIC-294 also skipped live checks). The owner decided: a service-account token, giving agents the same power as the owner (admin, write), with traceability. Do NOT add any auth bypass or dev-login switch. The token never travels in chat or task text.
