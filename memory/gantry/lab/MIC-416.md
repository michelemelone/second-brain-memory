## Request

1. When the owner edits and saves the title, the description or the acceptance criteria of a requirement that already has a delivery_slug, the requirement page shows a clear English banner saying the requirement was already released, that the change is saved in its Change log, and that the run cannot start until the change is validated. Verified by editing and saving a released requirement and by reading the banner on screen (screenshot with programs/bin/bigmike-shot gantry).
2. The banner carries the action that does it (open the validation of this change in the requirement's conversation and start it from there) and disappears once the change has been validated. Verified by using that action and by a screenshot before and after.
3. Validation is mandatory, not advisory: while a saved change is not validated, Start run is disabled in the table and on the requirement page, and the API refuses a direct start with a clear English error (409), so a run can never start on an unvalidated change. Verified by an API call on an unvalidated change, by the test asserting the refusal, and by the disabled control on screen.
4. The gate is per change, not one-off: after a validated change, any further change re-arms the block until that newer change is validated too. Verified by validating, changing again and reading the banner and the disabled button again.
5. The validating agent receives the diff of what changed: for each changed field (title, description, acceptance criteria) the previously delivered or last validated text and the new text, with the change taken from the latest Change log entry, so its analysis states what it saw differently from before. Verified by a backend test asserting the prompt content and by the validation answer naming the changed parts.
6. The validation runs from the requirement's conversation with the usual Validate action, its outcome is visible on the page, and the server records the validated revision of the content so the gate can be computed again after a reload. Verified by validating once, reloading and reading the same state.
7. A requirement that has never been delivered keeps today's flow unchanged (build it in conversation, validate when wanted, then Start delivery): the mandatory gate applies to a saved change on an already released requirement. Verified by a test and by the screen of a New requirement.
8. The owner is guided and never stuck: each state (change saved and unvalidated, validation running, validation done, run enabled) has one English line saying exactly what to do next, and no state is a dead end. Verified by walking the four states on screen and reading the lines.
9. Backend tests (the diff in the validation prompt, the 409 gate) and frontend tests pass, both builds pass; the work is committed, pushed and the Gantry restart is queued. Verified by the commands' output and the queue entry.
