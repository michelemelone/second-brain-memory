## Request

1. An item that already has a delivery_slug can be delivered again and the run really works: Start run produces run N+1 that executes the agents and ends with its own build, install and live-verification evidence. It never closes immediately with "Already released: there is nothing left to do". Verified on a real released item: state.json run 2 has status succeeded with evidence for the phases it redid, the run activity log shows the agents working, and the instance read-back shows the change.
2. The re-run starts from the earliest phase the change really touches (by default Build, reusing what is already delivered) instead of walking Intake and Design again; the run states in its activity which phases it re-opened and why. Verified by the run event list and by state.json before and after that run.
3. A run queued for a requirement released in the meantime still does nothing, while a deliberate Start run on a released requirement is never stopped by that guard; both cases are covered by automated tests. Verified by the test output naming both cases.
4. The agents of a re-run receive the previous run's delivery report and the change as it was asked (the latest Change log entry) in their prompt, so they change only what it touches. Verified by a runner test asserting the prompt and by the live run log.
5. Each run writes its own dated heading in PBI.md (Run 1, Run 2, ...) with start and end timestamp, outcome and the artifacts of that run; no earlier run is overwritten and run 1 stays byte-identical after run 2. Verified by reading PBI.md after two runs and by a diff.
6. The artifacts are the sum of every run: same PBI, same slug, same folder, same PBI.md; a re-run creates no new backlog item, no new folder and no sub-task. Verified by counting backlog items and requirement folders before and after.
7. Every item with a delivery_slug already present in the live data keeps its backfilled Run 1 entry in PBI.md, built from the existing state.json and evidence, so nothing delivered before is lost. Verified with a dry-run report over the 49 items and spot checks of three of them.
8. The requirement screen shows a Run history (number, date, state, link to the evidence of that run) and shows Start run instead of Start delivery when a run already exists; after run 2 the history shows both runs. Verified with screenshots in light and dark mode, desktop and phone.
9. A level-2 sub-task starts by itself when its parent reaches Released, without anyone pressing Start; a sub-task whose parent is not released stays New and states on screen why it has not started. Verified by putting one item in each situation and reading its state through the API and backlog.json.
10. While a run is working on an item, a chat change and Start run are refused with an explicit English message (API 409 with a clear body), and the controls are disabled on screen; when the run ends they come back. Verified by an API call during a run plus screenshots of the disabled controls.
11. A change written in chat on an already delivered item updates the item, appends its Change log entry in PBI.md and never starts a run by itself: the run starts only on Start run. Verified by making the change and checking that no run was created.
12. Backend tests, frontend tests and both builds pass; the work is committed and pushed and the Gantry restart is queued. Verified by the commands output and the queue entry.
