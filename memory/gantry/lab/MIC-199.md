- Project: Gantry
- Status: done
- Priority: medium
- Agent: Pegasus

## Request

Analyze requirements and evaluate frontend architectural impact for adding a List / Kanban toggle on the Gantry Board page. The feature must allow toggling between the current Kanban board and a tabular list view within the same screen for requirements currently in progress along the delivery pipeline and completed (Done), while leaving the Backlog in its own separate upstream section. Key aspects to define and verify: 1) Header toggle switch (e.g. Board / List icons) preserving active filters, sorting, and item selection across view modes; 2) List view columns displaying requirement ID, title, assignee, current pipeline stage badge, and status; 3) Reusability of existing Gantry board data models and state management. Deliver complete acceptance criteria and an implementation recommendation. Verify by cross-referencing existing Gantry frontend board code and state flow. Keep existing Kanban interactions and backlog segregation intact.

## Last report of the agent

I implemented the List / Kanban toggle on the Gantry Board and committed it, but I did not push it and it is not deployed yet.

**What I did**
- Added a Kanban / List toggle to the filter bar of `/board`, with the accessible labels "Kanban view" and "List view". The choice is saved in `localStorage` under `gantry.board.viewMode`, and the default is Kanban.
- Added `components/board/BoardTable.tsx`, a table built on the existing `DataTable`. It has these columns:
  - ID (backlog id, or the short REQ id when there is no backlog item)
  - Title (click to open the drawer)
  - Assignee
  - Stage, as a `StateBadge` with a pulsing dot while a run is going
  - Status, from `cardStatus`
  - Cost
  - Actions: Continue/Retry, Cancel, Back
- The list uses the same filtered `visible` cards as the Kanban. Search, application, iteration and feature filters, the open drawer and the notices all stay the same when you switch.
- I did not touch the Kanban markup or the backlog. I changed no backend code.

**Choices I made**
- No URL parameter, `localStorage` only.
- Actions are inline buttons, not a context menu.
- Back in the list reuses the same move path as the Kanban Back button.
