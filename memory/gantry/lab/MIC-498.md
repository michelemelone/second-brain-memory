## Request

Acceptance criteria (the assignee checks each one itself; the final report lists the evidence for every criterion):
1. Start run / Start delivery stays disabled while any point of the latest validation round is unresolved, of any severity (blocking or optional) and any kind (change or question), with the tooltip "Resolve the validation points in the Conversation before the run: N of M points resolved." Verified by a unit test on the gate (runGate.ts) and a frontend test.
2. The server refuses the run with 409 when a point of the latest round is open, for EVERY caller: the UI, the admin, a user, and the bigmike-service account with its Bearer token (the owner's impersonation by bigMike included). There is no bypass, no flag and no role that skips it. Verified by endpoint tests, one per caller type, plus a real call with the service token on a requirement with an open optional point (expect 409).
3. validationRequiredOf (backend/src/backlog/routes.ts) is true while any point of the latest round has no resolution, whatever the severity; an approved text with an open optional point no longer unlocks the run. Case to reproduce and fix: requirement #209 (round 2, one optional point never resolved, run started and released anyway).
4. The validation card stays open while points are open and closes as soon as all are resolved (applied, declined or answered), and it never shows "Accept as is" as enabled when the server would answer 409 "does not wait for a validation": the frontend condition and the server condition for "Accept as is, start anyway" are the same. Verified by a frontend test and a screenshot.
5. "Accept as is, start anyway" (from round 3 on) records every open point as accepted by the owner, unlocks the run and closes the card. Verified by a test.
6. Every point can be answered, applied or declined in every state, including after Release and on requirements started by the service account; the answer is stored, shown under its question, editable, and passed to the next validation round. Verified by a real API call and a test.
7. Process.md (the Unlock rule, line ~234), the validation prompt (when to use blocking, optional, question) and Gantry's brief state the new rule: no run while a point is open; the decision is also recorded in Gantry's lessons. Verified by the diff of those files.
8. The frontend and backend suites pass, the frontend is built and deployed from the latest commit, and the final report lists the measured evidence for each criterion above.

Context: owner decision 2026-11-26 in chat, replaces the MIC-437 rule that only BLOCKING points keep the gate armed. Related: MIC-437, MIC-446, MIC-429, MIC-468. Reference case: requirement #209 (Paws & Co), validation_rounds 2, round 2 with one optional "change" point unresolved, validation_outcome approved, run started and released.
