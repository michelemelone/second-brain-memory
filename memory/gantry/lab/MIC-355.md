# MIC-355: Gantry: cap the requirement hierarchy at two levels below the Feature (Feature = project container)

- Project: Gantry
- Status: done
- Priority: high
- Agent: Pegasus

- Updated: 2026-11-19

## Request

1. Feature = container (the equivalent of a Lab project), never a parent item: the Backlog and the requirement screen show the Feature only as a Feature column/filter and never build a parent-child chain from it. Verified on the Gantry Backlog screen with screenshots in light and dark mode, and by reading features.json and backlog.json.
2. A top-level item (requirement, bug or task) has related_to = null; a sub-task has related_to = the id of a top-level item. Verified by creating one of each through the UI and reading the API response and backlog.json.
3. The server rejects (HTTP 400, clear English message) any create or update that sets related_to to an item that already has related_to, i.e. that would create a third level. Verified with curl against the running API and with an automated integration test.
4. The server rejects a self-reference and any cycle. Verified with automated tests.
5. "Add change" and "Add bug" are available only on top-level items; a sub-task shows neither. Verified with screenshots of both screens and a component test.
6. The Backlog table renders exactly two levels below the Feature: the top-level row and one indented sub-task level, never a third level. Verified with a screenshot and a component test.
7. A one-off migration flattens every existing chain deeper than two levels: each level-3+ item is re-parented to the top-level ancestor of its chain, nothing is deleted and bundle_path is unchanged. Verified with a before/after report (counts per level) attached to the task, plus spot checks of at least three migrated chains.
8. Existing tests pass and the build passes (npm run build and npm test in backend and frontend). Verified by the commands' output.

Context and analysis
Michele's model, confirmed in chat: Feature in Gantry is like a project in the bigMike Lab. Below it there are at most two levels: level 1 = the requirement/bug/task (PBI), level 2 = its sub-task (change or bug). No level 3, ever.

Today the data model already has Feature as a separate store (features/featureStore.ts, feature_id on the item), so it is not a real parent. But related_to (the "Add change"/"Add bug" link) has no depth limit: it can point to any item, including one that already has related_to. The real data has 57 backlog items, 24 with a parent, including 6 at level 2 and 2 at level 3 — i.e. chains PBI -> change -> change -> change. The UI adds to the confusion by nesting follow-ups in the table.

The change is: enforce depth in the server (validate.ts + routes.ts), restrict the two buttons and the table nesting in the frontend, migrate the existing deep chains to level 2, and keep Feature visibly a container. Do not delete items, do not rename bundle paths: the documentation folders and the delivery runs depend on bundle_path.

Related tasks: MIC-205 (deep analysis of Gantry, includes the process findings), MIC-286 (UI parity with the Lab).
