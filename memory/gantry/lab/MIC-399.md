## What was wrong

The delivery agents stamp `phases.<name>.completed_at` with their own wall clock plus a `Z`, so run 1's stage times sat **one hour ahead** of the run itself (`11:52–11:56` instead of `10:52–10:56` UTC). Only `released` is written by Gantry with the real clock (`10:57:46Z`). Read together, Release landed before Test — hence `-3523 s`.

I chose to fix it **where the times are served**, not by rewriting stored data, so nothing about how runs are recorded changes (criterion 5) and the real minutes are kept: `backend/src/live/stageTimes.ts` turns each finished run into a window of real time (run ledger first, the state file's run list as fallback) and puts each stage time inside the run that produced it — kept if it fits, shifted by the smallest whole hour if that lands it in the run, at the run edge otherwise, and never before the stage preceding it. `GET /api/requirements/:slug/live` serves those times, so the Stage report, the per-stage table and the runs read one answer.
