## Request

1. Hierarchy is Feature (level 0 container, not a parent) plus at most one parent/child level underneath it; no item can be a grandchild of another item. Verified: API call and UI flow that try to set related_to of an item that already has a parent are rejected with a 4xx and a clear message; page screenshot.
2. "Add change" and "Add bug" are offered only on level-1 items (related_to = null); on a level-2 item the buttons are hidden and the server rejects the same operation if attempted directly (curl POST/PUT returns 4xx). Verified: curl transcript for both cases plus screenshots at desktop and phone width.
3. Every path that creates or updates items enforces the limit, including PUT /api/backlog/:id, the "Add change"/"Add bug" endpoints, and items created from a chat (general, feature and requirement chats) whose related_to is parsed from text such as "change #129". Verified: automated tests in the server test suite, one per path, all passing.
4. The existing data is repaired: every item below the second level (6 grandchildren and 2 great-grandchildren found today) is re-attached to the level-1 root of its chain, with related_to = root id. Verified: before/after table listing id, title, old related_to, new related_to.
5. The repair loses nothing: description, acceptance_criteria, application, feature, tags, status, delivery_slug and bundle_path are identical before and after for every touched item, and the bundle folder still exists. Verified: script that diffs every field before and after, reporting zero differences, plus `ls` of each bundle folder.
6. The repair is a one-shot, idempotent, dry-run-capable script committed in the repo, with a JSON report of what it changed. Verified: first run in dry-run changes nothing on disk; real run prints the report; second real run reports 0 changes.
7. The Board, the backlog table and the requirement detail page show the relationship with at most one indentation level, and a child shows its parent; a child never offers "Add change"/"Add bug". Verified: screenshots of board and table in dark and light theme, desktop and phone.
8. Documentation is aligned with the new model in the same change: Gantry's Process.md and the in-app help/tooltips describe Feature as the project container with at most two levels under it. Verified: diff of Process.md and screenshots of the help texts.
9. `npm run build` passes in Gantry programs/server and programs/web, the app is restarted through the project restart queue and the Board and a requirement page load without console errors. Verified: build output and pages loaded in the embedded browser.
