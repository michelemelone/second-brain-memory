## Request

ACCEPTANCE CRITERIA
1. The default stopping point of a delivery run (runner/runTrigger.ts, today 'built') is removed: after build and static check the run goes on, by itself, to install, read-back and release, with no stop at 'Ready to release' (backend test on the run phases; no deploy-kill guard of MIC-426 for the normal run).
2. Install: the requirement is deployed from its OWN worktree through the integration folder (main plus the deployed commits of the other requirements), as the batch release does today, never from the main folder; the deploy cap per run and the instance queue/lease are kept, so two requirements of one instance deploy one at a time (test with two requirements).
3. Read-back: after the deploy a minimal read-back (readBack.ts, as MIC-427) checks that the artifacts of the PBI exist, are active and updated at or after the deployment, and records sys_id and version in state.json; no tester agent and no live test are started (test).
4. Land: only after a successful read-back the branch is merged on main with landRequirement (main still builds, push done); the requirement becomes Released, PBI.md section 6 and a dated Change log entry are written, and the run is a numbered run of the PBI (MIC-363) (test + state.json of a real run).
5. A requirement that depends on an unreleased one waits (holdForOverlap / dependency check) and goes on by itself as soon as the dependency is released; a failed dependency holds back only the requirements that depend on it (backend test with a chain of three and one failing).
6. Failure: if build, install or read-back fails, nothing is marked Released, the worktree and branch stay, the requirement shows the reason (English, last output lines, credentials masked) and a Retry; a failed read-back never reinstalls (MIC-440) (tests).
7. The release stays on the dev instance only: production and UAT are refused as today (existing guard test).
8. The batch engine of MIC-427 (batchRelease, batchPlan, readBack, prepareSource) is reused as the release step of the run; the manual start (Release button and its route) is no longer needed by the flow but stays in the code until MIC-463 removes it (no duplicated release logic).
9. Requirement #162 (now Ready to release, change_pending) goes on to Release by itself after this change, or shows the reason it cannot (checked live with bigmike-gantry).
10. Requirements already Release/Installed are not touched (list before and after). Delete (MIC-452) still cleans a requirement released this way: its deployed ref exists (MIC-458) (test).
11. Backend tests and build pass; built from a clean checkout of the latest commit and deployed; the Gantry restart requested (say the commit built).

Context (owner decision 2026-11-25, option A of the study): everything is done end to end through worktrees that go to Release, with no manual step and no automated live test (the live check stays manual after release). Supersedes the manual batch model of MIC-426, MIC-427, MIC-428, MIC-431, MIC-432. Related: MIC-439 (worktree per requirement), MIC-440, MIC-441, MIC-452, MIC-458. UI is in MIC-463, docs in MIC-465, the live check in MIC-464. Use bigmike-gantry for the live API.
