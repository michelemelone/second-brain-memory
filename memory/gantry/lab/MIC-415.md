# MIC-415: Gantry: the Action button is enabled only when there is something to release

- Project: Gantry
- Status: todo
- Priority: high
- Agent: Pegasus

- Updated: 2026-11-20

## Request

1. A requirement that has never been delivered keeps the Action button enabled and starts its first delivery exactly as today. Verified by a test and by pressing the button on a New requirement.
2. A requirement that was already delivered and has no change saved since its last run (pending_run false) shows the Action button disabled and not clickable in the table, and Start run disabled on its requirement page, with an English title/tooltip saying there is nothing new to deliver. Verified by a frontend test and by a screenshot of a released, unchanged requirement in the table and on its page.
3. A delivered requirement with a change saved in its Change log since the last run (pending_run true) has the button enabled and starts the next numbered run. Verified by saving a change and pressing the button, and by a test asserting pending_run true enables it.
4. No start-run state is shown on a released requirement with nothing pending: neither the table row nor the requirement page shows a start-run affordance, banner or run note when pending_run is false and a delivery_slug exists (keeps MIC-400). Verified by a screenshot of a released unchanged requirement and by reading the rendered text.
5. While a run is in progress the button stays disabled and the requirement read only (keeps MIC-363), and the rule above comes back when the run ends. Verified by a test during a live run and by a screenshot of the disabled control.
6. The rule is decided by the server's state, not by the page's memory: a reload of the table and of the requirement page shows the same enabled or disabled button for the same requirement. Verified by reloading both screens on the three cases (never delivered, delivered and unchanged, delivered with a pending change).
7. Frontend and backend tests and both builds pass; the work is committed, pushed and the Gantry restart is queued. Verified by the commands' output and the queue entry.

Context and analysis
Michele: "il tasto action dovrebbe essere solo se c'è qualcosa di nuovo da rilasciare, cioè se è già stato rilasciato il tasto non è cliccabile... nel back end c'è ancora lo stato start run quando è release, ma io non ho modificato niente". Today frontend/src/components/backlog/BacklogTable.tsx disables the Action button only when item.delivering === true, and frontend/src/components/backlog/RequirementFormModal.tsx disables Start run only when saving, when the item is not loaded or while delivering: a released, unchanged requirement still offers a clickable run. The server already knows the truth: backend/src/backlog/types.ts pending_run ("a change has been saved in the Change log after the last delivery"), set in backend/src/backlog/routes.ts when a change is saved on an item with a delivery_slug and cleared in backend/src/backlog/backlogStore.ts when a run starts (markedRun). Related tasks: MIC-363 (numbered runs, edits locked while a run works), MIC-414 (the Actions column keeps only this button), MIC-400. Do not remove the possibility of a re-run after a change: only a requirement with nothing new is blocked.
