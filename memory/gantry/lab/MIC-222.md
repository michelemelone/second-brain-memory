## Verdict

| Question | Answer |
|---|---|
| Can Ask AI talk to the agent building the PBI? | **No.** |
| Can the chat use Ask AI with the PBI as context? | **Yes.** |
| Can it reach the agent in other ways? | **Yes, but only through three fixed actions, not as a conversation.** |

The three actions are answering an open question, starting a run, and reading the live feed.

## Why not

- **Ask AI is its own turn.** `POST /api/ask-ai/chats/:id/messages` (`chat/routes.ts:636`) starts a separate assistant turn, in `chat/askAi.ts`. It is not the process doing the build.
- **No link to the build.** A chat has no field tying it to a PBI or a build run. A search for subject, record or backlog-item fields in `chat/` found nothing.
- **Little context.** `askAiContext.ts` is the only place that builds context. It is called once, from `AskAiPage.tsx:272`. It sends a one-line-per-item summary of the backlog and the known applications: id, title, application, feature, state, delivery slug.
- **No agent channel.** `askAi.ts` has no code that reads the build agent's output or sends it a message. The Ask AI assistant is also read-only: its denied tools include Write, Edit, Task, Agent, WebFetch and WebSearch (`askAi.ts:342`).
- **One thing it can do for a record.** Its prompt (`askAi.ts:225`) says that when the context names a single record, `#<id>`, the chat can propose a change to it. That goes through `requirementProposal` with `updatesRequirementId`. The person must confirm it (`/ask-ai/messages/:id/action/confirm`, `chat/routes.ts:784`). This edits the record's fields, not the build.

## What the agent does expose

| Need | Route | Code path |
|---|---|---|
| Answer a question the agent is blocked on | `POST /api/requirements/:slug/answer` | `requirements/routes.ts:237`. It calls `repo.answer`, then `runTrigger.trigger` once every question is answered, so the work resumes by itself. |
| Start or continue a run | `POST /api/requirements/:slug/run` | `requirements/routes.ts:256` |
| Read live progress | `GET /api/requirements/:slug/live` | `live/routes.ts:36` |
| Admin-only validation chat | `POST /api/requirements/validation-chat` | `requirements/routes.ts:64`. It is a separate chat about a requirement, admin only (`policy.ts:296`). It is not a channel to the agent. |

The first two are permission-checked as `answer-approve` and `delivery-run` (`policy.ts:289`, `221`). The live route is read-only (`policy.ts:292`).

## Consequence for the new screen

- **Live and Open Questions (MIC-227):** use the routes above. Open Questions posts to `/answer`, which is the only real way to talk to the agent.
- **Ask AI:** use the existing Ask AI chat with a PBI-specific context string. It would be a new function next to `buildAskAiContext`. It would add the PBI's id, title, state, description, acceptance criteria, open questions and delivery slug. The chat is then a helper about the PBI, not the builder.
- **Free-text steering of the agent:** this needs new backend work, for example a queued "note to the agent" read at the next run. It is not in the MIC-217 option A plan. I recommend leaving it out of the eight tasks.
- **Wording:** label the centre chat "Ask AI about this PBI" so nobody thinks it steers the build.
