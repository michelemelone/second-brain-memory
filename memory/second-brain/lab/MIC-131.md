# MIC-131: UI brief for the Second Brain redesign

This brief comes from two standard-mode searches. It is a design brief only: no code was changed. Most sources are vendor guides and design systems, not formal standards. The Chameleon paper is the one research source for dark mode.

## Recommendations

**1. Show a clustered overview first, then expand on demand.**
- Open on a summary where nodes are grouped by type (people, projects, topics, decisions, preferences). Each group is one collapsed node showing a count.
- Expanding a cluster reveals its members, and a click focuses a node's neighbourhood.
- Filter and aggregate before applying a layout, and avoid showing the whole graph at once.
- Use a force-directed layout for the overview, because it shows global structure.
- Use a radial or focus layout for the local neighbourhood of the selected node.
- For graphs of 500 or more nodes, a practitioner source suggests stronger repulsion, explicit centring and a slower cooldown, so the graph doesn't collapse into a blob. This comes from a blog, so treat it as a starting point and test it.
- Don't overcorrect the spacing. Too much space between nodes also makes details hard to read.

**2. Declutter labels by importance and zoom level.**
- Show labels only for the hub nodes (the most-linked ones), the selected node and its neighbours. Reveal the rest as the user zooms in, and show a full label on hover.
- Dim non-neighbours when a node is selected, rather than hiding them, so context is kept.
- Add a wiki "card" side panel for the selected node, with summary, backlinks and source chat links. The IEEE VIS 2023 study of knowledge-graph practitioners points to knowledge cards that balance digestibility and discoverability.
- Consider a timeline view for the nightly wiki changes. The same study lists this as a research direction.
- The searches found no formal label-overlap rules, so the label thresholds are my own proposal. They need tuning on the real wiki.

**3. Tune dark and light palettes separately, and never rely on colour alone.**
- Define a paired palette for each theme. Don't just invert one. Datawrapper defines a dark counterpart for every colour in its light palette.
- Aim for at least 3:1 contrast for graph elements such as nodes and edges against the background. GitLab's palette steps target this on a dark surface.
- Aim for at least 4.5:1 for text (WCAG 2.1 AA), in both themes.
- Encode node type with shape, icon or label as well as colour, as American Express advises.
- Add outlines or halos to nodes, as Carbon does, to keep them readable.
- The Chameleon paper shows that simply converting a light chart to dark can break colour meaning and highlight contrast. Check the highlighted and selected states in both themes.

## Suggested next step
Pick one pilot: build the cluster overview with the label rules and the two palettes, and test it on the real wiki. Spacing and label thresholds should be set by looking at the actual graph.
