## Request

1. Ctrl+click (Windows/Linux) and Cmd+click (macOS) on a file or folder row toggles that row in/out of the selection without opening it, navigating or renaming anything; a plain click keeps today's behaviour (opens the item and clears any multi-selection). Verified by a new vitest component test in web/tests/multiselect.test.ts dispatching click events with ctrlKey:true and metaKey:true, plus a manual check in the running app (dev: npm run dev:web / npm run dev:server; live: memory.beedme.online port 3739) on Chrome and on a Mac trackpad setup.
2. Every selected row is visibly highlighted at the same time using the existing selected row style in web/src/styles.css, and the UI shows how many items are selected (e.g. '3 selected' in the explorer header/status); the count stays correct as items are added or removed from the selection. Verified by screenshot of a 3-item selection and by a component test asserting the counter text.
3. Right-click on an already selected row opens the existing FileMenu with the whole selection preserved; right-click on an unselected row selects only that row and opens the menu for it; no action is ever applied to an item the user did not select. Verified by component tests on the contextmenu handler in web/src/Tree.tsx and by manual right-clicks in the app.
4. When more than one item is selected, the FileMenu (web/src/FileMenu.tsx) shows only actions that are meaningful for a selection and runs each of them on ALL selected items in one action: Make a copy, Move to..., Delete, Copy path (all selected paths, one per line), Bookmark/Remove bookmark; single-item actions (New note, New folder, Search in folder, Rename) are disabled/greyed out with a tooltip explaining they need a single item; no menu entry silently does nothing. Verified by a component test asserting the enabled/disabled state of every entry for 1 vs 2+ selected items and by visually opening the menu on a multi-selection.
5. Delete on a multi-selection asks for confirmation naming the number of items, then deletes every selected file and folder (folders recursively, as the existing single delete already does), with the tree, editor tabs and bookmarks updated; no item is left behind. Verified by a test asserting one delete call per selected item (or one bulk call) and a manual run on a scratch folder under second-brain/ checking the files are really gone on disk.
6. Move to... on a multi-selection asks for the destination once and moves every selected file/folder into it, skipping/erroring clearly on name conflicts and never leaving a half-moved set without an error message; the tree refreshes to the final state. Verified in the app by moving 3 notes to another folder and confirming on disk with `ls`, plus a unit test of the bulk move handler.
7. Make a copy on a multi-selection copies every selected item using the existing copy-naming scheme, and Bookmark/Remove bookmark applies to all selected notes and persists in the bookmarks store (folders are skipped for bookmarks with a clear message). Verified by a test of both handlers and a manual check that the copies exist and the bookmarks survive a page reload.
8. Pressing Escape or clicking an empty area of the explorer clears the multi-selection, and the selection is cleared automatically after a bulk action completes; a single-item selection still behaves exactly as today. Verified by test (keydown Escape clears state) and manual check.
9. Nothing regresses: single-item right-click menu, drag-and-drop move between folders (MIC-324), upload, search and keyboard navigation still work, and `npm test`, `npm run typecheck` and `npm run build` in /home/beedme/data/workspace/second-brain-app all pass with the new tests included.

What to do: implement multi-selection state in the Second Brain explorer (web/src/Tree.tsx, FileMenu.tsx, ContextMenu.tsx, ExplorerActions.tsx) and, where a bulk operation needs it, a batch endpoint in server/ (also touch web/src/writeApi.ts/api.ts) so N items are moved…
