## Request

Problem (owner, 2026-11-18, in Italian, summarised). Memory is centralised in the Second Brain app, not in bigMike. The owner wants a "mega summary" per application, but only of the important things: what the application is, what has been done, the decisions that matter, and how an agent must intervene to change it. The summary must be short enough to be injected into every agent run, and it must be built from the Second Brain and live there, so it is the single source of truth. Today there is no such file: the only injectable context is the wiki index (clipped at 6,000 characters), 8 recent Lab tasks clipped to 220 characters, and the monthly data summaries for Health and Finance.

This task produces the per-application brief as a documented artifact and its first real content. Injection into bigMike prompts is a separate task that depends on this one.

Acceptance checklist (report done / not done for each point):
1. Define the brief contract in writing: file memory/<app>/BRIEF.md; hard cap 4,000 characters (target 2,500-3,500); English; no secrets and no raw personal data. Sections, in this order: What it is; Stack and where the code lives; Where the data lives; Current state; Decisions that constrain changes; Recent work (last 3-5 items with task keys); Known pitfalls; How to verify and restart. Header line with "Updated: YYYY-MM-DD" and the list of sources it was built from.
2. Evidence rule: every claim comes from the Second Brain (Lab history, memory wiki, project documents, monthly summaries, chats). Each item cites the task key or file path it comes from. When the material exceeds the cap, condense the least important parts first; never drop a decision or a pitfall to save space, and never silently truncate.
3. Define who refreshes it and when, in the Second Brain README (and in the brief itself): after a Lab task of that application finishes, or by an explicit refresh run; the existing brief is the input and is compressed/updated, not rewritten from zero. The refresh must not depend on reading the bigMike database directly and must not keep a second copy in bigMike.
4. Create memory/health/BRIEF.md and memory/finance/BRIEF.md with real content, even though those Lab projects have no task history yet: read the application repository, its README/docs, the existing monthly summaries and the wiki pages projects/health and projects/personal-finance. State clearly when something is unknown rather than inventing it.
5. Create BRIEF.md for bigMike and Second Brain from their existing Lab history, wiki pages and docs. For Gantry, respect MIC-13 (excluded from the Second Brain): choose the compliant place (for example under memory/bigmike/lab/gantry/) and justify it, or leave Gantry without a brief and say why.
6. Create or update memory/README.md as the global index: at most 2,000 characters, one line per application saying what it is and which brief to read first. This is the always-injectable shared layer.
7. Verify by reading: someone with no knowledge of the repository can, from the brief alone, say where the code and data are, which decisions constrain a change, how to test it and how to restart it. Check every brief is within the cap, has no secrets, and cites its sources. Put the character count of each brief in the final report.
8. Git: commit and push every repository that changed (second-brain, and the nested memory repository if touched), after checking the branch is not behind; never force.

Rules: English artifacts; only Markdown views in the Second Brain; do not duplicate the brief inside bigMike. Related tasks: MIC-196 (memory layout), MIC-13 (Gantry exclusion), the layout task this depends on, and the injection task that follows.
