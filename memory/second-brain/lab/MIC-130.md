## What exists today
- **Engine panel:** the Second Brain app already has its own copy in `web/src/SettingsPanel.tsx`. It has a hard-coded list of 4 engines and models, and it saves through `PUT /api/memory/wiki-agent`. That call is forwarded to bigMike by `delegateToMemory` in `server/src/app.ts`. bigMike's own panels are `ModelsSettings.tsx` and `OpencodeModelsSettings.tsx`. Nothing is shared between the two apps.
- **Agents ↔ memory:** only `POST /api/memory/ask`. It makes one bare model call, with no tools, on excerpts the browser already found. Agents have no way to search or read the memory themselves.
- **Auth:** the Second Brain app has no sign-in of its own. It only checks the Cloudflare Access token (`authenticate` in `app.ts`) and returns a bare `401 {"error":"unauthorized"}`. The web app has no handling for a 401: `grep` finds no `401`, `unauthorized` or `login` in `web/src`.
- **bigMike's memory routes:** `auth.ts` there lets `/memory/*` through without a bigMike session when the call comes from the machine itself (`isLocalHost`) and carries no Cloudflare headers. Through the tunnel, a valid Access token is enough.
- **Reload:** `POST /api/memory/index` runs `memoryIndexRun()`. That runs `refreshMemoryDirs()` and then indexes every memory source, so one call re-reads the whole library. There is no way to reload only the bigMike chat-wiki folder (`WIKI_MEMORY = "chat"`).

## 1. Engine panel
| Option | How | Pros | Cons | Effort |
|---|---|---|---|---|
| A | Keep the copy. Fetch the engine and model list from bigMike (a new `GET /api/memory/engines`) instead of the hard-coded list. | Small, no new package, never out of date | Still two panels | S |
| B | Extract a shared `EnginePanel` package used by both apps. | One panel | Needs a package or monorepo and a build change in two repos | L |
| C | Embed bigMike's panel in an iframe. | No code | Cross-origin sign-in problems, breaks the "own app" rule | M |

**Recommendation: A.** It removes the stale-list risk, which is the real problem. B only pays off if a third app needs the panel.

## 2. Connecting agents to memory
| Option | How | Pros | Cons | Effort |
|---|---|---|---|---|
| A | Read-only HTTP tools on bigMike: `GET /memory/search` and `/memory/page` already exist. Add a short "how to query the memory" skill file so agents call them. | Uses what exists, costs no extra tokens | The agent has to run curl | S |
| B | An MCP server wrapping search and page. | Clean for the engines that support MCP | New moving part, and not every engine supports it | M |
| C | Inject excerpts into every prompt. | Nothing for the agent to do | Spends tokens on every run, which goes against the "spend tokens only on purpose" goal | S |

**Recommendation: A**, with agents getting read access only. The raw Finance and Health data stays in each app.

## 3. Login fix
I can't tell from the code alone which failure Michele sees. Three candidates:
- **Expired session:** a `401` from `/api/*` leaves the page stuck, with no redirect to the Cloudflare login. Fix: in `api.ts`, on a 401, reload the page, which sends the browser through Cloudflare Access.
- **Wrong AUD tag:** a new Access application for this app needs its own `CF_ACCESS_AUD`. If it holds bigMike's tag, every call is rejected. bigMike's verifier accepts a comma-separated list; this one accepts a single value.
- **Forwarding:** `delegateToMemory` passes `cf-access-jwt-assertion` to bigMike, but bigMike's `/memory/*` path then goes through the Cloudflare check and not the local bypass. If the app calls bigMike by its LAN address, the local bypass should apply.
